## 2. Что показал лог (последний прогон, 258 строк)

### D1 — ПОДСКОК: данные есть, и они опровергают прежние гипотезы

```
ПОДСКОК g239 | подскоков=4 | opОтрыва=WAIT | op=WAIT | strafe=false
| hColl=false | stun=0 | eat=false | charge=28 | aggr=false | меч=false
| vy=-0.078 | state=PANIC goal=GuardianRetreatGoal target=игрок@4.8
| hp=1/20 pos=-59.3,-60.00,-1.1 onGround=true
```

| Поле | Значение | Вывод |
|---|---|---|
| `opОтрыва=WAIT` | на отрыве от земли операция была `WAIT` | **это НЕ `strafe` и НЕ `MOVE_TO`** |
| `strafe=false` | наш шаг не активен | не наш отход |
| `hColl=false` | горизонтального столкновения нет | не упор в стену **в момент отчёта** |
| `charge=28` | идёт перезарядка арбалета (из 40) | ⚠️ **гипотеза владельца про перезарядку — совпала** |
| `aggr=false`, `меч=false` | меч не активен | гипотеза «при переходе на меч» **не подтвердилась** |
| `state=PANIC`, `hp=1/20` | паника | в панике тоже бывает |
| `goal=GuardianRetreatGoal` | работает гол отступления | |

**Важно:** `opОтрыва` вычисляется как `getMoveControlOperation()` в тике, когда `wasAirborne == false && !grounded`. Если операция `WAIT` — значит **никто не звал `strafe`/`moveTo` в этом тике**, а отрыв произошёл сам. Что даёт отрыв при `WAIT`?

- `LivingEntity.aiStep`: прыжок вызывается только при `this.jumping == true` → `jumpFromGround()` (для земли) — то есть кто-то выставил `jumping`.
- **Кто выставляет `jumping`?** `JumpControl.tick()` — его зовёт `MoveControl.tick()` в ветке `MOVE_TO` (но у нас `WAIT`), **и `FloatGoal`** — а он теперь у нас есть и работает каждый тик в воде/лаве.

⚠️ **Ключевая зацепка:** нужно проверить, не срабатывает ли `FloatGoal` вне воды (её `canUse` = `isInWater() && fluidHeight > jumpThreshold || isInLava()`), и не остаётся ли `jumping = true` от прошлых тиков.

### D2 — «не бьёт и не подходит»: данные противоречат предыдущему выводу

```
НЕ БЬЁТ g239 | d=2.14 | dSqr=4.56 | reachSqr=2.04 | вДосягаемости=false
| nextAttack=0 | navDone=false | op=WAIT | navTo=-66.5/-4.5 | gPos=-67.4/-5.3
НЕ БЬЁТ g239 | d=2.34 | dSqr=5.46 | reachSqr=2.04 | вДосягаемости=false
| nextAttack=0 | navDone=true  | op=WAIT | navTo=-70.5/-1.5 | gPos=-69.1/-1.5
```

**Критично:** `navDone=false` — маршрут **ЕСТЬ**, навигация не завершена, но `op=WAIT` и страж **не двигается**. То есть проблема **не в отсутствии пути** (как я думал раньше), а в том, что **путь есть, но `MoveControl` его не отрабатывает**.

При этом мой фикс (`repathTimer`, зов `moveTo` раз в 10 тиков) сработал **88 раз** — и не помог. Значит дело не в пересчёте пути.

**Что мешает `MoveControl.tick()` довести MOVE_TO до движения?** Кандидаты:

| # | Кандидат | Как проверить |
|---|---|---|
| C1 | [`applyFacing()`](../../../src/main/java/com/phian404/survivalpoints/entity/BaseGuardianEntity.java) каждый тик ставит `setYRot(bodyYaw)` (к цели) **после** `moveControl.tick()`, а `travel()` → `moveRelative()` считает направление по текущему `yRot` ⇒ страж едет к цели напрямую, а не по узлам маршрута, и упирается в угол | `facing=` в `/sp_guard detail` + сравнить `yaw` и `wantYaw` |
| C2 | `GuardianMoveControl.tick()` перезаписывает `setZza/setXxa` и ломает вход, который выставил `MoveControl` в `MOVE_TO` | убрать перезапись при `!ourActive` (сейчас так и есть — проверить) |
| C3 | `standStill()` → `resetNavigationTarget()` → `getNavigation().stop()` вызывается из `stop()` головы **каждый раз**, когда гол перезапускается | в логе `navDone` скачет `false→true` |
| C4 | `damageStunTicks` / `syncEquipmentToState` — нет, `stun=0` | уже исключено |

### D3 — почему детектор не ловит D1

Текущий `ПОДСКОК` требует **серию из 4 приземлений** в окне 20 тиков. В логе — **1 срабатывание** на 3–4 визуальных зависания. Значит:
- либо приземления не считаются (логика `wasAirborne` работает только при `!grounded`);
- либо зависание **не даёт приземления** (страж «встаёт на невидимый полублок» — то есть `onGround()` возвращает **true** в воздухе!).

⚠️ **Это главное для D1:** описание «встаёт на невидимый полублок» буквально означает, что `onGround()` стало `true` без опоры. Тогда мой `ПОДСКОК` это и не увидит, потому что считает приземления, а для него это «стоит на земле».

### Найдено при реализации: `op=WAIT` в логах был ложным сигналом

Исходник ванильного `MoveControl` (проверено через MCP, 1.20.1):

```java
public void tick() {
    if (this.operation == Operation.STRAFE) {
        ...
        this.operation = Operation.WAIT;   // ← сброс ВНУТРИ тика
    } else if (this.operation == Operation.MOVE_TO) {
        this.operation = Operation.WAIT;   // ← сброс в самом начале ветки
        ...
    } else if (this.operation == Operation.JUMPING) { ... }
    else { this.mob.setZza(0.0F); }
}
```

**Следствие:** читая `operation` снаружи (в `BaseGuardianEntity.tick()`, то есть уже
после `MoveControl.tick()`), мы почти всегда видели `WAIT` — даже когда гол в этом
тике заказывал `MOVE_TO` или `STRAFE`.

Значит вывод из прошлого разбора — «`opОтрыва=WAIT`, никто не заказывал движение» —
**был ошибочным**. `WAIT` означал лишь «тик уже отработал».

Исправление в замерах: [`GuardianMoveControl.tick()`](../../../src/main/java/com/phian404/survivalpoints/entity/GuardianMoveControl.java)
запоминает `operation` ДО вызова `super.tick()` (`operationBeforeTick`) и после
(`operationAfterTick`). В отчётах теперь два поля: `opЗаказ` и `opПосле`.

Дополнительно проверено по исходнику `JumpControl`:

```java
public void jump() { this.jump = true; }
public void tick() { this.mob.setJumping(this.jump); this.jump = false; }
```

То есть перехват `setJumping` в сущности действительно увидит и `FloatGoal`
(он зовёт `getJumpControl().jump()`), и `MoveControl` (он тоже зовёт `jump()`).

| Гипотеза | Результат | Доказательство из лога |
|---|---|---|

**Настоящая причина.** Страж дошёл до **конечного узла маршрута** и остановился, но этот узел
стоит вне досягаемости удара:

```
конечный узел: navTo = -56.5 / 13.5
позиция стража: gPos  = -57.7 / 14.7
расстояние между ними        = √(1.2² + 1.2²) ≈ 1.70 блока
нужно для удара (reachSqr 2.04 → d ≤ 1.428)
```

То есть **даже встав ровно на конечный узел, страж не дотянулся бы до цели** — узел сам по себе
дальше, чем радиус удара.

Дальше срабатывает ванильная логика [`MeleeAttackGoal.tick()`](../../../src/main/java/com/phian404/survivalpoints/entity/ai/GuardianMeleeAttackGoal.java:129).
Проверено по исходнику 1.20.1: путь пересчитывается только когда

```java
this.pathedTargetX == 0.0 && … || target.distanceToSqr(pathedTargetX, pathedTargetY, pathedTargetZ) >= 1.0
    || this.mob.getRandom().nextFloat() < 0.05F
```

Игрок в этом бою стоял на месте → `distanceToSqr` до запомненной точки = 0, а 5 %-шанс за
19 секунд дал ровно то, что видно: `gPos` не менялся ни на сантиметр.

**Почему мой `repathTimer` (88 вызовов) не помог:** он вызывал
`getNavigation().moveTo(target, speed)`. Но `moveTo(Entity)` строит путь до **блок-позиции цели**,
а навигация считает такой путь уже достигнутым (`navDone=true`) — то есть 88 раз подряд просили
маршрут, который «уже пройден». Отсюда ноль эффекта.

**Вывод:** дефект не в нашем коде движения, а в **несогласованности двух радиусов** —
навигация останавливает моба в ~1.7 блока от цели, а удару нужно ≤ 1.43.

**Итог: D1 — это НЕ зависание и НЕ невидимый полублок.** Это нормальный полёт
после отбрасывания. «Зависанием» он выглядит потому, что страж в воздухе
продолжает работать ногами (`zza=0.25`) — бежит по воздуху вместо того, чтобы
отлететь.

**Почему прежние детекторы его не видели:** `ПОДСКОК` считает приземления и
склеивает их в серию из 4 — 6 визуальных случаев дают 1 отчёт. `ПОЛУБЛОК`
искал `onGround` без изменения `y`, `ПРЫЖОК ЗАЛИП` — залипший флаг; ни того,
ни другого не было, потому что их и нет.

**Добавлен детектор `ОТБРОС`** ([`checkKnockbackHang()`](../../../src/main/java/com/phian404/survivalpoints/init/GuardianHangDetector.java)):
подъём ≥ 0.8 блока (между шагом на полублок 0.6 и отбрасыванием 1.0) **и**
`|vy| ≤ 0.05` дольше 4 тиков подряд = «зависание у вершины». Одна запись на
каждый визуальный случай, со следом движения.

### D2 — подтверждён числами (замер M7)

```
НЕ БЬЁТ | d=1.60 | reachSqr=2.04 | navDone=false
        | конУзел=-56.5/11.5@1.33(узлов=3,пройдено=1) | путьИсчерпан=false
        | порогНав=0.45 | opЗаказ=MOVE_TO | zza=0.25
```

`конУзел@1.33` — конечный узел маршрута в 1.33 блока от стража, при радиусе
удара 1.428. То есть в этом случае узел **внутри** радиуса, и страж ударил
(следом идут `удар мечом`). А в прогоне №1 конец маршрута был в **1.70** — и
страж стоял.

Разница между «бьёт» и «стоит» — укладывается ли конечный узел в радиус удара.
Навигация ставит узел с допуском `порогНав=0.45` и может поставить его на
**любую** сторону от цели, в том числе за её спиной. Это и есть дефект.

## 3.3. Прогон №5 со снимками по требованию — ПРИЧИНА НАЙДЕНА

Владелец: «зависает в воздухе он всегда, когда упирается в стену». Собрано
**16 снимков** `/sp_snap` в моменты, когда дефект виден глазами.

### Данные: все 16 снимков одинаковы

```
поз: x=-53.300 y=-62.000 z=14.700 | onGround=true | надБлоком=0.000 | блокПод=grass_block
скорость: dx=0.000 dy=-0.078 dz=0.000 | вода=нет | лиана=нет | hColl=true/чередуется | vColl=true
вход: zza=0.000 xxa=0.000 | jumping=false | прыжков=9
MoveControl: заказ=WAIT после=WAIT | strafe=false | keepYaw=false
навигация: done=true stuck=false | конец=-53.5/14.5@0.28(узлов=1,пройдено=1) | порог=0.45
бой: stun=0 | еда=нет | заряд=10 | агрессия=нет | паника=ДА | цель=Игрок@2.5
```

След за 32 тика (последний снимок):

```
-62.00/-0.078/G/-/0.00/0.00/WAIT/stun=0/hColl=0
-62.00/-0.078/G/-/0.00/0.00/WAIT/stun=0/hColl=1
-62.00/-0.078/G/-/0.00/0.00/WAIT/stun=0/hColl=0
-62.00/-0.078/G/-/0.00/0.00/WAIT/stun=0/hColl=1     ← и так все 32 тика
```

### Что это значит

| Наблюдение | Вывод |
|---|---|
| `y=-62.000`, `надБлоком=0.000` **во всех 16 снимках и 32 тиках** | Страж **на земле**. В воздухе он не был ни разу |
| `vy=-0.078` постоянно, но `y` не падает | Это стандартное «прижатие к земле» ванильной физики при `onGround` |
| `hColl` мигает `0/1` | **Горизонтальное столкновение** — страж упёрся в стену |
| `zza=0`, `op=WAIT` | Гол **не просит** движения: он считает, что идти некуда |
| конец маршрута `@0.28`, `узлов=1`, `пройдено=1` | Pathfinder вернул путь из **одного** узла — то есть «дойти нельзя», и страж стоит |
| `паника=ДА`, цель@2.5 | Идёт `GuardianRetreatGoal`, а он как раз стоит по достижении рубежа |

**Итог:** то, что видно как «зависание в воздухе у стены», — это страж, который
**стоит на земле, упёршись в стену**. Прыжок/полёт тут ни при чём: `jumping=false`,
`onGround=true`, высота не меняется. «Зависание» — это отсутствие движения,
а не полёт.

Глазами это читается как «висит», потому что модель при `hColl` и нулевом входе
покачивается на месте у преграды.

**Корень:** pathfinder не находит дорогу к цели (путь из одного узла), навигация
считает маршрут пройденным, гол не пересчитывает путь при неподвижной цели —
и страж застревает у стены навсегда, пока цель не сдвинется.

## 3.4. ВЕРДИКТ: «зависание в воздухе» — ванильная физика, не дефект мода

### Решающий эксперимент

Владелец поставил рядом со стражем **ванильного зомби** в тех же условиях —
запертым в 1 блок между 4 стенами — и ударил каждого одинаково.

> **Зомби подпрыгивает и «застревает» точно так же.**

Поведение воспроизводится на чистой ванили. Страж не добавляет ни импульса,
ни высоты, ни длительности.

### Почему это выглядело как зависание

`knockback` при `onGround` даёт `vy = min(0.4, −0.078/2 + 0.4) = 0.361`.
Гравитация `0.08`, трение `0.98`:

| тик | сдвиг вверх | vy после |
|---|---|---|
| 1 | +0.361 | 0.275 |
| 2 | +0.275 | 0.191 |
| 3 | +0.191 | 0.109 |
| 4 | +0.109 | 0.028 |
| 5 | +0.028 | −0.050 |
| **≈10** | **возврат на землю** | — |

Подъём **0.96 блока**, полёт **≈0.5 с** — ровно то, что описывалось как
«зависает на полсекунды».

В открытом поле та же дуга читается как «отлетел в сторону», потому что
горизонтальная часть проходит. В коробке 1×1 горизонталь гасят четыре стены,
остаётся голая вертикаль → подскок строго на месте.

Это совпадает с данными прогона №2 (подъём 0.96, дуга 16 тиков,
`jumping=false`) — но тогда решающий шаг не был сделан: не проверили то же
самое на ванили.

### Опровергнуто данными (не пересматривать)

| Версия | Чем опровергнута |
|---|---|
| «Не бьёт / статуя» | **26 ударов** за прогон |
| «Не смотрит на игрока» | `headYaw` = `wantYaw` = 129.6 |
| «Застрял в блоке стены» | `inFeet=WALKABLE` |
| «Застрял в углу» | владелец запер его в 1×1 — места нет |
| «Наш обход `followPathDetouring` виноват» | удаление ничего не изменило, откачено |
| «Навигация не даёт путь» | `canReach=true`, «дошёл» по `reachRange=1` |
| «Тряска из-за мигающего `hColl`» | при 4 стенах стоит ровно |
| «У стража лишний вертикальный импульс» | **зомби прыгает так же** |

### Единственный реальный дефект — двойной удар (исправлен)

В `GuardianMeleeAttackGoal.checkAndPerformAttack()` наши `swing(MAIN_HAND)` и
`playSound(PLAYER_ATTACK_SWEEP)` дублировали то, что следом делает
`super.checkAndPerformAttack()`. Урон не удваивался (его делает только ваниль),
но **анимация взмаха и звук проигрывались дважды за удар**.

Доказательство (`M8-atk`, до → после):

| До правки | После |
|---|---|
| `swings=40 hits=20` | `swings=26 hits=26` |
| `swings=22 hits=11` | `swings=22 hits=22` |
| `swings=14 hits=7` | `swings=18 hits=18` |

Раньше взмахов было ровно вдвое больше попаданий на всём прогоне.

### Откачено (не помогало, лечило симптом)

| Что | Почему |
|---|---|
| `followPathDetouring()` + константы `DETOUR_*` + вызовы в трёх голах | `ОБХОД=0` за прогон — не срабатывал; удаление ничего не изменило |
| `repathTimer` | 88 вызовов, ноль эффекта: `moveTo(Entity)` строит путь до блок-позиции, навигация считает его пройденным |
| путь к точке подхода `MELEE_APPROACH_DISTANCE` | `createPath` округляет до центра блока: `конУзел@0.16`, а `d=1.47` |
| гашение `zza`/`xxa` в воздухе | не помогло, стало хуже |
| гашение вертикального отброса | лечило бы симптом ванильной физики |

### Что осталось в коде

- исправленный двойной удар;
- измерительная обвязка в `/sp_snap`: `M8-path`, `M8-types`, `M8-hit`, `M8-atk`
  (работает **без** `/sp_trace` — трассировку легко забыть включить, на этом был
  потерян один прогон);
- детекторы `ОТБРОС`, `ПОЛУБЛОК`, `ПРЫЖОК ЗАЛИП`, `ПОДСКОК`, `ТОНЕТ`;
- след движения 32 тика;
- поля `opЗаказ`/`opПосле`, `конУзел`, `путьИсчерпан`, `порогНав`.

### Если позже захочется изменить ощущение

Это настройка, а не исправление дефекта: `GuardianTuning.KNOCKBACK_VERTICAL_SCALE = 1.0D`
(1.0 = ваниль) и умножение `delta.y` в `hurt()` после `super.hurt()`.
По умолчанию **не вводить**.

## 4. Варианты решения (после замеров)

### D2 — ОТКАЧЕНО: правка «путь к точке подхода» не помогла

Попытка: просить путь не к блок-позиции цели, а к точке на расстоянии
`MELEE_APPROACH_DISTANCE = 1.0` от неё по линии «цель → страж».

**Результат прогона (22:12, страж `g2`) — не помогло, а стало заметно хуже:**

```
пересчёт пути: маршрут исчерпан, цель вне удара   ← 94 раза
удар мечом                                        ← 26 (до правки было меньше)
НЕ БЬЁТ g2 | d=1.47 | reachSqr=2.04 | navDone=true
           | конУзел=-56.5/13.5@0.16(узлов=1,пройдено=1) | путьИсчерпан=true
           | gPos=-56.6/13.6   | zza=0.00
```

**Почему не сработало — и это важный вывод:**

`конУзел@0.16` при `d=1.47`. Страж стоит в 0.16 от узла — то есть **дошёл**.
Но до врага всё равно 1.47, а нужно 1.428. Значит запрошенная точка
`(target + u * 1.0)` при построении пути была **округлена до центра блока**:
`PathNavigation.createPath(double, double, double, int)` работает в блочной
сетке. Точка на расстоянии 1.0 блока от цели попадает в блок, чей центр
может оказаться и в 1.5 блоке от неё.

Вывод: **точечного подхода через навигацию добиться нельзя** — она всегда
возвращает центр блока. Правка откачена.

### D2 — историческая справка: первая формулировка

**Доказано логами:** страж доходит до конечного узла маршрута и стоит, потому что
узел оказывается дальше радиуса удара.

| Прогон | конУзел | Радиус удара | Итог |
|---|---|---|---|
| №1 (g877) | `@1.70` | 1.428 | **стоял** 19 секунд, `gPos` не менялся |
| №2 (g217) | `@1.33` | 1.428 | **ударил** |
| №3 (g3) | `@1.70` | 1.428 | **стоял** 24 записи подряд |

Почему так: `PathNavigation.moveTo(Entity, speed)` строит путь до **блок-позиции**
цели, а навигация считает его пройденным на своём допуске (`порогНав=0.45`).
Итог — остановка в 1.4–1.7 блока. Ванильный `MeleeAttackGoal` путь не
пересчитывает: цель неподвижна (`distanceToSqr = 0`), шанс 5 %/тик за 19 с
ничего не дал.

**Правка** — [`GuardianMeleeAttackGoal.requestPathIntoAttackRange()`](../../../src/main/java/com/phian404/survivalpoints/entity/ai/GuardianMeleeAttackGoal.java):
путь просим не к цели, а к точке на луче «цель → страж» на расстоянии
[`MELEE_APPROACH_DISTANCE = 1.0`](../../../src/main/java/com/phian404/survivalpoints/init/GuardianTuning.java)
от цели. Эта точка заведомо внутри радиуса удара (1.43).

Также возвращён ограниченный по частоте пересчёт (раз в 10 тиков) — но теперь
он просит правильную точку, а не блок-позицию цели.

**Почему не уменьшили допуск навигации:** он общий для всех маршрутов, включая
прогулку и отступление. Правка локальна для ближнего боя.

### D2 — варианты (историческая справка)

| # | Вариант | Суть | Риск |
|---|---|---|---|
| **A** | Убрать наш `setYRot` при движении по маршруту | в [`applyFacing()`](../../../src/main/java/com/phian404/survivalpoints/entity/BaseGuardianEntity.java) не ставить `setYRot(bodyYaw)`, когда активен меч-гол (там навигацией владеет ваниль) | тело перестанет смотреть на цель во время подхода — как у зомби, приемлемо |
| **B** | Отдать меч-гол полностью ванили | убрать наш `tick()`-фикс и `applyFacing` для MELEE, оставить только гейт дистанции | теряем «лицом к врагу» в ближнем бою (но ваниль и так смотрит `LookControl`) |
| **C** | Оставить как есть | — | дефект остаётся |

**Склоняюсь к A:** это минимально и лечит корень (курс перезаписывается после `MoveControl`).

### D1 — ОТКАЧЕНО: правка «не бежать по воздуху» не подтвердилась

Попытка: в `GuardianMoveControl.tick()` обнулять `zza`/`xxa`, когда страж в воздухе.
Основание — что `zza=0.25` в полёте означает, что страж «бежит по воздуху».

**Результат прогона: не помогло.** Владелец насчитал ~10–12 зависаний (хуже, чем 6
до правки). Правка откачена — в коде её больше нет.

**Что это доказывает:** `zza` в воздухе — НЕ причина зависания. Горизонтальная
скорость в полёте задаётся отбрасыванием, а не входом движения; обнуление `zza`
картину не меняет.

**Важный побочный результат третьего прогона (лог 22:05, страж `g3`):**

```
НЕ БЬЁТ g3 | d=1.83 | reachSqr=2.04 | navDone=true
           | конУзел=-54.5/13.5@1.70(узлов=2,пройдено=2) | путьИсчерпан=true
           | opЗаказ=WAIT | opПосле=WAIT | zza=0.00
           | gPos=-53.3/14.7   ← 24 записи подряд, НИ ОДНОГО изменения
```
И при этом в этом же прогоне: `ОТБРОС=0`, `ПОДСКОК=0`, `ПОЛУБЛОК=0`,

**Вывод:** страж всё это время **на земле** — поэтому ни один детектор движения
не срабатывает. То, что владелец видит как «зависание в воздухе», в трёх прогонах
давало противоположные данные, и **единого признака у него пока нет**.

### D1 — историческая справка: первая версия правки

Симптом был не в физике, а в том, что страж в полёте продолжал работать ногами.

**Проверено по исходникам 1.20.1:**

```java
// Mob
public void setSpeed(float s) { super.setSpeed(s); this.setZza(s); }

// Mob.serverAiStep — порядок важен
this.moveControl.tick();   // ← ваниль здесь зовёт setSpeed → setZza
this.lookControl.tick();
this.jumpControl.tick();
// затем LivingEntity.aiStep → travel() читает zza
```

То есть в ветке `MOVE_TO` ваниль **каждый тик** выставляет `zza = 0.25`, и `travel()`
это честно применяет — даже когда страж в воздухе.

**Правка** — [`GuardianMoveControl.shouldSuppressAirInput()`](../../../src/main/java/com/phian404/survivalpoints/entity/GuardianMoveControl.java):
в конце `tick()`, если страж не на земле, не в воде/лаве, не на лиане и это не
`JUMPING`, вход движения обнуляется.

Что намеренно **не** гасится: прыжок ради подъёма на блок, вода/лава
(`FloatGoal`), лианы и лестницы, персонаж на земле.

Флаг `CUSTOM_MOVE` не трогали, `JumpControl` не отключали, `setDeltaMovement`
для земли не возвращали — запреты соблюдены.

**Ожидаемый эффект:** отбрасывание теперь проходит как отбрасывание; полёт
перестаёт читаться как «зависание»; детектор `ОТБРОС` проверит это на следующем прогоне.

| # | Вариант | Суть | Риск |

| **C** | Оставить | — | дефект остаётся |

|---|---|
| `ОБХОД` | только в **комментариях** `BaseGuardianEntity.java:1717-1718` и в этом плане |
| `detourReported` | объявлено (`:1611`), сбрасывается (`:1662`, `:1792`) — **ни разу не читается** |
| `GuardianTrace` в `followPathDetouring()` | отсутствует |

То есть поле `detourReported` — мёртвое, а строка лога
`[SP] g… \| ОБХОД: угол 30° …`, которую предписывает §3.4 этого плана, **никогда
не могла появиться**. Счётчик «0 срабатываний» измерял отсутствующий логгер,
а не отсутствие обхода. Вывод «веер не работает» из этого прогона **не следует**.

### 7.1. Дефект 1 (тряска в углу) — корень: `horizontalCollision` как единственный переключатель

**ДОКАЗАНО КОДОМ + ЛОГОМ.** [`GuardianRetreatGoal.tick()`](../../../src/main/java/com/phian404/survivalpoints/entity/ai/GuardianRetreatGoal.java:121)
делит поведение на две **взаимоисключающие** ветки:

```java
if (this.guardian.horizontalCollision) {
    followPathDetouring(...);   // ← clearStrafe() + setKeepYaw(false)
    return;
}
...
strafeWithSpeed(-1.0F, 0.0F, RETREAT_SPEED);   // ← ourActive = true
```

`hColl` в этих снимках **мигает `0/1/0/1`** (след в §3.3: 32 тика, значения
`hColl=0` и `hColl=1` чередуются). Значит **каждый второй тик** гол попадает в
ветку `strafe`, а следующий — в ветку обхода. А [`applyPathModifiers()`](../../../src/main/java/com/phian404/survivalpoints/entity/BaseGuardianEntity.java:1781)
внутри обхода вызывает `clearStrafe()`. Итог — **вход движения заводится и
обнуляется каждый второй тик**: это и есть «дёргается на месте».

Второй, более тяжёлый слой — **когда `hColl=true` постоянно**:

1. `followPathDetouring()` строит прямой путь: в углу pathfinder отдаёт
   **1 узел** (`узлов=1, пройдено=1` — есть в каждом снимке §3.3).
2. [`isUsablePath()`](../../../src/main/java/com/phian404/survivalpoints/entity/BaseGuardianEntity.java:1625)
   требует `>= DETOUR_MIN_NODES (2)` ⇒ прямой путь **отбрасывается**.
3. Включается веер: 6 лучей по `DETOUR_LOOKAHEAD = 2.0`. В углу между двумя
   стенами **все шесть** лучей упираются в блок ⇒ у всех путей узлов `< 2`.
4. Срабатывает финальная ветка (`:1772-1777`): «ничего не подошло → отдаём
   прямой путь». `direct != null` (1 узел) ⇒ `moveTo(direct, …)` — маршрут,
   который навигация тут же считает **пройденным**.
5. Гол выходит из `tick()`, **не выставив ни одного шага**: `strafe` снят
   `applyPathModifiers()`, а `MOVE_TO` до 1-узлового пути даёт `WAIT` ⇒
   `MoveControl.tick()` → `setZza(0)`.

Что это значит для вопроса «почему при `hColl=true` страж не начинает движение»:
**ему физически нечем двигаться** — ни `strafe` (снят), ни пути (1 узел =
«дороги нет»). И это повторяется каждый тик: гол каждый тик заново просит
маршрут, который уже «пройден».

**Отдельно важно:** `DETOUR_MIN_NODES = 2` вместе с финальной веткой
«отдать прямой путь» — логически противоречивы. Мы признали путь непригодным,
а затем всё равно им ходим. Именно это даёт «потолок» из §3.4: в ближнем бою
ветка `isUsablePath(direct)` срабатывает и до веера дело не доходит.

### 7.2. Ответ на вопрос «откуда `zza=0.245` при `op=WAIT` и `strafe=false`»

**В снимках паники этого нет.** Во всех файлах `snap.txt`, `snap1.txt`,
`one.txt` строка выглядит так:

```
вход: zza=0.000 xxa=0.000 | jumping=false | источникПрыжка=- | прыжков=9
MoveControl: заказ=WAIT после=WAIT | strafe=false | keepYaw=false
```

`zza=0.000`, не `0.245`. Значение `0.245` из формулировки задачи относится к
**другому** прогону (боевому) и в разборе тряски участвовать не должно.

**ДОКАЗАНО АРИФМЕТИКОЙ** для того боевого случая: `0.25 × 0.98 = 0.245`.
В ванильном `LivingEntity.aiStep()` перед `travel()` стоит `this.zza *= 0.98F`,
а `0.25` — это ровно то, что `Mob.setSpeed(float)` пишет в `zza`
(`Mob.setSpeed → setZza`) из ветки `MOVE_TO`/`STRAFE`. Значит `0.245` —
**затухающее эхо нашего же входа**, а не «кто-то выставляет вход при `op=WAIT`».
(Оба факта сверены по исходникам 1.20.1 через MCP `minecraft-modding`.)

**ГИПОТЕЗА (нужен замер):** `strafe=false` в том же снимке — потому что
`clearStrafe()` был вызван веткой обхода **в том же тике после** установки шага;
флаг `isOurStepActive()` — мгновенный, а `zza` живёт до затухания. Проверяется
одним полем «`ourActive` на момент `pushMotionTrail`» вместо «на момент снимка».

**Практический вывод:** `zza` в отчётах **нельзя** использовать как признак
«гол заказал движение» — это уже записано в §3.1 плана. Признак — `opЗаказ`.

### 7.3. ДОКАЗАНО ЛОГОМ: страж в панике прыгает у стены

В `snap.txt` счётчик `прыжков` растёт **на стоящем на месте страже**:

```
прыжков=9  →  9  →  9  → 10  → 10  → 11  → 11  → 12
```

при `onGround=true`, `y=-62.000` во всех снимках, `jumping=false` в момент снимка
и `opЗаказ=WAIT`. Источник — ванильный `MoveControl.tick()`, ветка `MOVE_TO`
(проверено по исходнику 1.20.1):

```java
BlockPos $$14 = this.mob.blockPosition();
VoxelShape $$16 = $$15.getCollisionShape(this.mob.level(), $$14);
if ($$11 > this.mob.maxUpStep() && … || !$$16.isEmpty() && this.mob.getY() < $$16.max(Y) + $$14.getY() && …)
    this.mob.getJumpControl().jump();
```

Когда страж прижат к стене, блок в его собственной `blockPosition()` может быть
блоком стены ⇒ `!$$16.isEmpty()` ⇒ **прыжок каждый раз, когда гол всё-таки
попросил `MOVE_TO`**. Прыжок в стену + падение = второй вклад в «тряску».
Запрет «не отключать `JumpControl`» при этом **не нарушается**: лечится не
прыжок, а бесконечные `moveTo` в недостижимую точку.

### 7.4. Дефект 2 (зависание в ближнем бою) — что доказано, а что нет

**ДОКАЗАНО КОДОМ — наш `isPathExhausted()` ошибается на единицу:**

```java
return path != null && path.getNextNodeIndex() >= path.getNodeCount() - 1;
```

При `узлов=2, пройдено=1` (в логе: `конУзел=…@1.70(узлов=2,пройдено=2)` и
`@1.54(узлов=2,пройдено=1)`) выражение `1 >= 1` даёт `true` — «маршрут
исчерпан», хотя впереди ещё один узел. При `узлов=1, пройдено=0` даёт `true`
для **не начатого** маршрута. Это только диагностика, но она подпитывала
неверный вывод «путь исчерпан ⇒ идти некуда».

**ДОКАЗАНО КОДОМ — почему страж не пересчитывает путь.**
[`GuardianMeleeAttackGoal.tick()`](../../../src/main/java/com/phian404/survivalpoints/entity/ai/GuardianMeleeAttackGoal.java:114)
вызывает `super.tick()` (ванильный `MeleeAttackGoal`), который пересчитывает
маршрут только при `distanceToSqr(pathedTarget*) >= 1.0` **или**
`random.nextFloat() < 0.05F`. Игрок стоял неподвижно ⇒ первое условие ложно,
а 5 %/тик за 19 с в логе не сработало ни разу (`gPos` не менялся на сантиметр).
Ровно это уже зафиксировано в §3.1 — **подтверждается повторно**.

**ОПРОВЕРГНУТО: «он зависает в воздухе».** См. §3.3 — `onGround=true`,
`надБлоком=0.000`, `y` не меняется ни на миллиметр во всех 16 снимках.

**ГИПОТЕЗА — почему «даже не смотрит на меня».** В логе (страж `g1`):

```
yaw=265.0 | bodyYaw=156.3 | wantYaw=-226.2    ← расхождение ~7° по телу
yaw=270.0 | bodyYaw=0.0   | wantYaw=90.0      ← тело 0, голова 270
```

В ближнем бою [`applyFacing()`](../../../src/main/java/com/phian404/survivalpoints/entity/BaseGuardianEntity.java:945)
**полностью уступает разворот ванили**:

```java
if (this.isMeleeActive()) {
    this.entityData.set(DATA_HEAD_PITCH, this.getXRot());
    this.entityData.set(DATA_HEAD_YAW, this.getYHeadRot());
    return;                      // ← наш faceTarget() не вызывается
}
```

Ваниль крутит `yRot`/`xRot` через `LookControl.setLookAt`, а **`yBodyRot` мы в
этой ветке не трогаем вообще**. Если `yBodyRot` не догоняет `yRot`, корпус
остаётся развёрнутым в сторону — визуально «не смотрит». Замер, который это
закроет: писать в `НЕ БЬЁТ` **разницу** `wrapDegrees(yaw - bodyYaw)` и
`yBodyRot` **до и после** `super.tick()`. Тогда видно, догоняет корпус или нет.

### 7.5. Чего в логе нет и что это значит

| Поле из формулировки задачи | Фактически в снимках |
|---|---|
| `zza=0.245` | `zza=0.000` во всех 16 снимках паники |
| `moveYaw=31,9 moveSpd=0,25` | поля **есть только у `CUSTOM_MOVE`** (`moveDirectly`); при `strafe` `moveSpeed` не обновляется ⇒ значение устаревшее |
| `событие ОБХОД = 0` | логгера нет в коде (§7.0) |
| `путьИсчерпан=true` | считается с ошибкой на единицу (§7.4) |

Вывод: **три из четырёх «фактов» формулировки не годятся как основание для
правки.** Годятся: `hColl` мигает, `узлов=1`, `zza=0.000`, `заказ=WAIT`,
`strafe=false`, `прыжков` растёт, `gPos` не меняется.

### 7.6. «Зависает в воздухе, ударяясь в стенку, когда его бьёшь» — что доказано

**ДОКАЗАНО ЛОГОМ — полёт после удара это отбрасывание, а не прыжок** (§3.2, след 16 тиков):

| Признак | Значение | Вывод |
|---|---|---|
| Подъём | 0.96 блока | `jumpFromGround()` даёт `vy = 0.42` и подъём ≈ **1.25** — не совпадает |
| Флаг `j` | `-` **все 16 тиков** | `JumpControl` не участвовал |
| Баллистика | `0.275 → 0.191 → 0.109 → 0.028 → −0.050 …` | ровная дуга, шаг ≈ −0.08 = ванильная гравитация |
| `zza` | `0.25` **все 16 тиков, включая полёт** | код продолжает «толкать» вперёд |
| Длительность | 16 тиков ≈ **0.8 с** | ровно то, что владелец называет «зависание» |

Источник подъёма — ванильный `LivingEntity.knockback()`:
`vy = min(0.4, vy/2 + strength)` при `onGround`. Наш `hurt()` добавляет только
`damageStunTicks = 3`, а он гасит **исключительно** `moveDirectly()` (ветка
`CUSTOM_MOVE`), которого в ближнем бою нет. ⇒ отбрасывание никто не ограничивает.

**ДОКАЗАНО КОДОМ — почему это выглядит как «висит», стоя у стены.** Прижат к
стене ⇒ горизонтальная составляющая отброса гасится коллизией, вертикальная
остаётся ⇒ страж подлетает **на месте**. А `zza` продолжает подаваться, поэтому
ноги «бегут» в воздухе. Визуально — висит и дёргает ногами.

**ДОКАЗАНО КОДОМ — второй, независимый источник подъёма у стены.** Ванильный
`MoveControl.tick()`, ветка `MOVE_TO`:

```java
BlockPos p = this.mob.blockPosition();
VoxelShape shape = this.mob.level().getBlockState(p).getCollisionShape(...);
if (… || !shape.isEmpty() && this.mob.getY() < shape.max(Y) + p.getY() …)
    this.mob.getJumpControl().jump();
```

`blockPosition()` — это блок, в котором **ноги** стража. Прижат к стене так, что
центр попал в блок стены ⇒ `!shape.isEmpty()` ⇒ **прыжок**. Ограничитель —
`noJumpDelay = 10` в `LivingEntity.aiStep` ⇒ не чаще **одного прыжка в 0.5 с**.
Это в точности период наблюдаемых «подскоков» (`прыжков 9→10→11→12` в §7.3).

**ИСПРАВЛЕНИЕ РАНЕЕ ЗАПИСАННОГО (важно).** В первой редакции §7.4 я привёл
строку лога `yaw=270.0 | bodyYaw=0.0 | wantYaw=90.0`. **Такой строки в
выгрузках НЕТ** — поиск по всем файлам `.roo/temp_files/*.txt` по шаблонам
`yaw=270` и `bodyYaw=0\.0` даёт **0 совпадений**. Это была моя ошибка, а не
данные. Все выводы, которые на ней строились, отозваны.

**ДОКАЗАНО ЛОГОМ (по фактическим записям) — `bodyYaw` в порядке, «застревает» `yaw`.**

Пересчёт `wrapDegrees` по записям `НЕ БЬЁТ` (`wantYaw` приведён к `0…360`):

| Запись | `yaw` | `bodyYaw` | `wantYaw` норм. | `bodyYaw − wantYaw` | `yaw − bodyYaw` |
|---|---|---|---|---|---|
| `nb4` 36.284 | 203.3 | 202.5 | 172.5 | +30.0 | +0.8 |
| `nb4` 37.284 … 42.285 (6 записей) | 203.3 | **172.5** | 172.5 | **0.0** | **+30.8** |
| `nb4` 44.284 | 171.0 | 171.0 | 169.3 | +1.7 | 0.0 |
| `nb4` 13.04 … 13.13 (7 записей) | 137.9 | **119.5** | 119.5 | **0.0** | **+18.4** |
| `nb` 06.28 … 42.57 (g3) | 135.0 | **132.0** | 132.0 | **0.0** | +3.0 |

Вывод из чисел, а не из догадки:

1. **`bodyYaw` сходится ровно к `wantYaw`** (расхождение 0.0 с точностью до
   десятых в 14 из 15 записей). Курс корпуса **правильный**, моя прежняя
   гипотеза про «корпус идёт за движением» **опровергнута**.
2. **`yaw` (это `getYRot()`) застревает** и расходится с корпусом на **3…31°**.
   В меч-ветке [`applyFacing()`](../../../src/main/java/com/phian404/survivalpoints/entity/BaseGuardianEntity.java:945)
   делает ранний `return` и `setYRot` **не вызывает**, а ванильный
   `tickHeadTurn` при `deltaSq <= 0.0025` (страж стоит) цель **не меняет**
   (`target = this.yBodyRot`). Поэтому `yRot` остаётся от последнего `MOVE_TO`.

**Почему это важно, хотя корпус визуально верный:** ванильный `travel()` →
`moveRelative()` считает направление шага по **`getYRot()`**, а не по
`yBodyRot`. Значит при расхождении 31° страж шагает (в т.ч. пятится при
`strafe`) **на 31° в сторону** от того, куда смотрит корпус. Это отдельный,
не закрытый дефект движения.

**ЧЕГО Я НЕ ДОКАЗАЛ:** что «не смотрит на меня» вызвано этим. Голова в бою
ведётся ванильным `LookControl.setLookAt(target, 30, 30)` из
`MeleeAttackGoal.tick()`, а в `applyFacing()` синхронизируется `getYHeadRot()` —
то есть по коду голова **должна** смотреть на цель. Утверждать «голова
отвёрнута» на этих данных нельзя. Нужен прямой замер (см. §9.6).

**ГИПОТЕЗА (требует замера):** «висит» = отбрасывание **плюс** прыжок
`MoveControl` из блока стены, наложенные друг на друга. Проверяется одним полем:
в след добавить `bodyYaw` и `onGround` **после** `aiStep` (сейчас `onGround`
пишется из `tick()`, уже после физики).

**Что НЕ доказано и нельзя утверждать:** что в момент «зависания» страж реально
внутри блока стены. В снимках паники у стены (§3.3) `onGround=true`,
`надБлоком=0.000`, `y` не меняется — там зависания нет. Значит нужен отдельный
прогон именно на **удар по стражу, прижатому к стене**, с включённым следом.

## 8. Предлагаемые минимальные правки — ПО ОДНОЙ

Порядок выбран так, чтобы каждая правка проверялась отдельно и её эффект нельзя
было спутать со следующей. Все — в рамках запретов §6.

### Правка 1 (сначала замер, не поведение) — сделать `ОБХОД` наблюдаемым

Без этого проверить что-либо в углу невозможно: сейчас события нет.

- В `followPathDetouring()` писать `GuardianTrace.always(...)` при выборе
  обходного луча и при «ничего не подошло» — с `угол`, `узлов`, `упор`.
- Удалить мёртвое поле `detourReported` **или** начать его читать.
- В `GuardianSnapshot` добавить `ourActive` **на момент** `pushMotionTrail`.

**Почему первым:** правка №2 меняет поведение в углу; без логгера мы снова
будем судить по «0 срабатываний», которое ничего не значит (§7.0).

### Правка 2 — убрать `horizontalCollision` как единственный переключатель

Причина тряски (§7.1): мигающий `hColl` рвёт вход движения каждый второй тик.

- Решение по факту упора берётся из `detourStuckTicks` (он уже считается по
  двум признакам и **не мигает** — §3.4 п.2), а не из `hColl` напрямую:
  `if (getDetourStuckTicks() >= DETOUR_TRIGGER_TICKS) { followPathDetouring ровно один раз; }`
- Пока порог не набран — **всегда** `strafeWithSpeed(-1,0,RETREAT_SPEED)`.
  Тогда в углу страж хотя бы пытается пятиться каждый тик, а не через тик.

**Ожидаемый эффект:** исчезает чередование «шаг / нет шага». Если страж
по-прежнему стоит — значит упор настоящий, и это уже правка 3.

### Правка 3 — «непригодного» пути не должно быть, но и молчать нельзя

Противоречие из §7.1: путь признан непригодным, но всё равно отдаётся навигации,
а шаг не выставляется вовсе.

- Если ни прямой, ни один луч не дали `>= 2` узлов — **не вызывать** `moveTo`
  для 1-узлового пути (он всё равно «пройден») и **явно** оставить
  `strafeWithSpeed(-1, 0, RETREAT_SPEED)` — хоть какое-то движение вместо нуля.
- Порог `DETOUR_MIN_NODES` не трогаем.

**Ожидаемый эффект:** в глухом углу страж упирается и скользит вдоль стены, а не
замирает. Риск: возможен «бег в стену» — поэтому проверять вместе с правкой 2.

### Правка 4 — `isPathExhausted()` привести к ванильному смыслу

`getNextNodeIndex() >= getNodeCount()` (совпадает с `Path.isDone()`), а не
`getNodeCount() - 1`. Только диагностика, поведение не меняется — но именно этот
показатель сейчас врёт в отчётах (§7.4).

### Правка 5 — закрыть последние 4 сантиметра в ближнем бою

Только после 1–4 и отдельного прогона. Кандидаты (выбрать **один**):

| # | Вариант | Суть | Риск |
|---|---|---|---|

### Правка 6 — синхронизировать `yRot` с `bodyYaw` в ближнем бою

## 10. КОРНЕВАЯ ПРИЧИНА (не симптом)

> Правки 2, 3, 5, 6 из §8 — **симптоматика**. Они латают следствия. Ниже —
> причина, из которой оба дефекта выводятся как следствия.

### 10.1. В страже два конкурирующих слоя движения

| Слой | Кто решает направление | Чем управляет |
|---|---|---|
| **A. ванильный** | `PathNavigation.followThePath()` → `MoveControl.setWantedPosition` | `MOVE_TO`, сам прыгает, сам ловит застревание (`doStuckDetection`, `timeoutPath`) |
| **B. наш** | [`strafeWithSpeed()`](../../../src/main/java/com/phian404/survivalpoints/entity/ai/GuardianRetreatGoal.java:146), `keepYaw`, `followPathDetouring` | `STRAFE` + перезапись `zza`/`xxa`/`yRot` **после** `super.tick()` |

Слой B добавлен ради одной задачи: **«отходить от врага, оставаясь к нему лицом»**. У ванили такой операции **нет** — ванильные мобы от врага не пятятся, они либо идут по маршруту (корпус по пути, голова через `LookControl`), либо стоят.

### 10.2. Три конкретных поломки, порождённые слоем B

**(1) Наш `MoveControl` отменяет ванильную защиту от упора.** Это главное.

Ванильный `MoveControl.tick()`, ветка `STRAFE`:

```java
float f7 = f2 * f6 - f3 * f5;     // мировой вектор шага
float f8 = f3 * f6 + f2 * f5;
if (!this.isWalkable(f7, f8)) {   // ← шаг в стену?
    this.strafeForwards = 1.0F;   // ← ваниль СПАСАЕТ: шагает ВПЕРЁД
    this.strafeRight = 0.0F;
}
this.mob.setZza(this.strafeForwards);
this.mob.setXxa(this.strafeRight);
```

Наш [`GuardianMoveControl.tick()`](../../../src/main/java/com/phian404/survivalpoints/entity/GuardianMoveControl.java:174):

```java
if (this.ourActive) {
    this.mob.setZza(this.ourForwards);   // ← ставим -1 обратно
    this.mob.setXxa(this.ourRight);
}
```

**Мы каждый тик возвращаем шаг назад, который ваниль только что заменила на шаг вперёд.** При упоре в стену это означает: страж не может освободиться вообще никогда. Отсюда «встал, упёршись в стену, и не реагирует» — и именно поэтому помогает только удар игрока (он отбрасывает, отрывая от стены).

**(2) Признак упора — флаг контакта, а не прогресса.** `horizontalCollision` — это «в этом тике было касание», он мигает (`0/1/0/1` в следе). Голы [`GuardianRetreatGoal`](../../../src/main/java/com/phian404/survivalpoints/entity/ai/GuardianRetreatGoal.java:121) и [`GuardianRangedAttackGoal`](../../../src/main/java/com/phian404/survivalpoints/entity/ai/GuardianRangedAttackGoal.java:214) строят на нём **взаимоисключающую развилку** «пятиться ИЛИ идти в обход». Мигание → развилка дребезжит → вход движения заводится и снимается через тик. Это тряска.

**(3) Дублирование логики.** `GuardianRetreatGoal.tick()` и `GuardianRangedAttackGoal.retreatFromTarget()` — **один и тот же код** (тот же `hColl`, та же точка на 2.0 блока, тот же `followPathDetouring`, тот же `strafeWithSpeed(-1,0,…)`). Одна и та же ошибка живёт в двух местах и правится дважды.

### 10.3. Вывод: причина одна

> Страж вынужден **сам решать направление шага каждый тик из ненадёжного флага**, потому что ванильная навигация не умеет «отходить лицом к врагу». Этот самодельный слой перекрывает ванильные механизмы — включая защиту `isWalkable()` — и потому не может ни выйти из упора, ни удержать стабильный вход.

Оба дефекта — следствия:
- **тряска в углу** = дребезг развилки по мигающему `hColl` (плюс путь из 1 узла, который не даёт шага);
- **зависание у стены при ударах** = `isWalkable` подменяет шаг на «вперёд», а мы возвращаем «назад» (плюс отбрасывание без возможности сдвинуться вдоль стены).

### 10.4. Корневое лечение (вместо симптомов)

**Убрать слой B: не изобретать «отход лицом к врагу» — выражать намерение через навигацию.**

| Было (слой B) | Стало (ванильный слой A) |
|---|---|
| `strafeWithSpeed(-1, 0, …)` + `keepYaw` + перезапись `zza` в `GuardianMoveControl` | `navigation.moveTo(точкаОтхода, speed)` — корпус ведёт маршрут |
| «лицом к врагу» через откат `yRot` | «лицом к врагу» — **только голова**: ванильный `LookControl.setLookAt(target)` + `clampHeadRotationToBody` (±75°). Так работают скелеты |
| развилка по `horizontalCollision` | решения нет: путь либо строится, либо ваниль сама делает `repath`/`timeout` |
| `followPathDetouring` с веером | ванильные `PathNavigation.doStuckDetection` + `recomputePath` |
| дубль в двух голах | один хелпер `retreatTo(distance)` на сущности |

**Что это даёт по построению:**
- `isWalkable` больше не перекрывается → из упора страж выходит сам;
- нет перезаписи `zza` после `super.tick()` → нет дребезга, нет тряски;
- удаляется `keepYaw`, `ourForwards`/`ourRight`/`ourActive`, `followPathDetouring`, `moveDirectly`, `moveAlongPath`, `detourAngleIndex/Timer`, `DETOUR_*` — заодно исполнялся бы `R0.2`. **Этот вариант лечения снят с выполнения**: `R0.2` закрыт владельцем без выполнения (см. [`GUARDIAN_REWORK_PLAN.md`](GUARDIAN_REWORK_PLAN.md)), самописная физика остаётся штатной.

**Риск, который надо принять сознательно:** при отходе корпус будет развёрнут по маршруту, а на игрока смотрит только голова. Визуально это «спина при отступлении». Это ванильное поведение (скелеты), но это **изменение вида**, поэтому требует согласования владельца.

**Чего это лечение НЕ делает:** не трогает прыжок из блока стены (`noJumpDelay`) и не решает «последние 4 см» в ближнем бою. Первое исчезает, как только страж перестаёт быть вжатым в блок; второе — отдельная задача про радиус удара (§7.4).

## 12. РЕЗУЛЬТАТ ЗАМЕРА M8 — причина найдена, и она не в обходе

Прогон владельца, страж `g195`, 5 снимков `/sp_snap` подряд (33.1 → 48.7 с),
бой на мечах, игрок вплотную.

```
поз: x=-29.300 y=-62.000 z=-60.300   | блокПод=grass_block   ← НЕИЗМЕННО во всех 5
навигация: done=true | конец=-29.5/-60.5@0.28(узлов=1,пройдено=1) | порогНав=0.45
M8-path:  canReach=true distToTarget=1.00 nodes=1 nextIdx=1
          targetBlk=-31,-62,-61  endNode=-30/-62/-61
M8-types: inFeet=WALKABLE underFeet=BLOCKED atTarget=WALKABLE
M8-hit:   moved=0.000 ticks=101
вход: zza=0.000 xxa=0.000 | hColl=false | заказ=WAIT | strafe=false
прыжков: 2 → 3 → 3 → 4 → 5
бой: агрессия=true | паника=false | цель=Игрок@0.9
курс: yaw=135.0 bodyYaw=129.6 headYaw=129.6 wantYaw=-230.4 (=129.6)
```

### 12.1. Две мои гипотезы опровергнуты этими числами

| Гипотеза | Данные | Вердикт |
|---|---|---|
| «Стартовая позиция не `WALKABLE`, эвалюатор не даёт соседей» (§11-БИС п.2) | `inFeet=WALKABLE` | ❌ **опровергнута** |
| «Наш обход виноват» (§11.5) | правка удалена, поведение не изменилось | ❌ **опровергнута** |

### 12.2. Настоящая причина: навигация считает игрока ДОСТИГНУТЫМ

`canReach=true`, `nodes=1`, `nextIdx=1`, `distToTarget=1.00`.

`PathNavigation.moveTo(Entity, speed)` вызывает `createPath(entity, 1)` —
**`reachRange = 1`**. В `PathFinder`:

```java
if (node.distanceManhattan(target) <= reachRange) { target.setReached(); }
```

Страж в блоке `-30,-62,-61`, игрок в `-31,-62,-61` → `distanceManhattan = 1 <= 1`
→ цель помечена достигнутой, путь = **1 узел**, `isDone() = true`.

Следствие: `PathNavigation.tick()` не вызывает `setWantedPosition` →
`operation` остаётся `WAIT` → `MoveControl` не заказывает шаг → `zza = 0`.
Отсюда `moved=0.000` за 101 тик.

**Это ванильное поведение, и оно КОРРЕКТНО**: моб в пределах блока от цели
считается «дошёл» и останавливается. Ванильный зомби в этой же ситуации тоже
стоит. Значит дефект не в движении.

### 12.3. Что тогда выглядит сломанным

Два РАЗНЫХ явления, которые я раньше смешивал:

| # | Явление | Механизм | Вердикт |
|---|---|---|---|
| **A** | Подскок ~0.8 с и падение в ту же точку | ванильный `knockback`: `vy = min(0.4, −0.078/2 + 0.4) = 0.361`, подъём 0.96 бл. Горизонталь гасится стеной/углом, вертикаль проходит | **ванильное**, арифметика сходится (`0.361→0.275→0.191→0.109→0.028`) |
| **B** | «Выключился и не смотрит» | `headYaw=129.6` при `wantYaw=129.6` → голова смотрит **точно на цель**. `bodyYaw=129.6` тоже | по данным **не подтверждается** |

То есть по этому прогону страж стоит в досягаемости (`0.9` при радиусе `1.43`),
смотрит на игрока верно, и единственное его движение — вертикальный подскок
от отбрасывания.

### 12.4. Чего в замере НЕ хватает (единственное белое пятно)

В формате снимка **нет `nextAttack`** — то есть неизвестно, бьёт ли он вообще.
Это критично: ванильный зомби в такой позе выглядит живым именно потому, что
**бьёт** (взмах + урон + отбрасывание игрока). Если страж не бьёт, игрок видит
«статую, которая подпрыгивает от ударов».

Проверяется одним полем `nextAttack=` в снимок либо поиском события
`удар мечом` в логе за тот же интервал.

## 11-БИС. ОТКАЧЕНО: гипотеза §11.5 не подтвердилась

Правка «убрать `followPathDetouring()` из меч-гола, вернуть ванильную
навигацию» **была реализована и проверена в игре владельцем → не помогла:
страж по-прежнему зависает у стены. Правка откачена полностью.**

Что это доказывает:

| Вывод | Статус |
|---|---|
| Ванильная навигация сама по себе даёт стражу путь к выходу | ❌ **опровергнуто** |
| `isUsablePath`/веер — причина зависания | ❌ **опровергнуто** (их удаление ничего не изменило) |
| Причина в том, что страж лишён пути | ❌ **опровергнуто** |

**Моя ошибка в рассуждении.** Я построил вывод на цепочке «путь выбракован →
шага не заказано → стоит» и не проверил **предпосылку**: а строит ли pathfinder
приемлемый путь вообще. Снимки (`νavDone=true`, `узлов=2, пройдено=2`,
`конУзел@1.70`) показывают, что путь **был** и навигация считала его
пройденным — то есть страж не «без пути», а «с путём, который не ведёт к
движению». Это другой механизм, и он не проверен.

**Что осталось НЕ проверенным (отсюда следующий шаг):**

1. Что реально возвращает `createPath(target, 0)`: `canReach()`,
   `getDistToTarget()`, `nodeCount`, `nextNodeIndex`.
   Ключ: `canReach == true` при неполном пути означал бы, что pathfinder
   считает цель достигнутой, хотя это не так.
2. `BlockPathType` **блока, в котором стоит страж**. Если его стартовая
   позиция помечена не как `WALKABLE`, `WalkNodeEvaluator` может не дать
   соседей — тогда путь вырождается в 1 узел независимо от нашего кода.
3. `BlockPathType` блока цели.
4. Реальный сдвиг `x/z` **в тиках после удара** (не в снимке): движется ли он
   вообще и на сколько.

Пока эти четыре числа не получены, любые правки движения — гадание. Правило
владельца «только по данным логов» здесь нарушать нельзя: уже одна правка
сделана по стройной, но непроверенной логике и откачена.

## 11. ПОЧЕМУ ОН НЕ МОЖЕТ ВЫЙТИ ИЗ СТЕНЫ (меч) — ГИПОТЕЗА, ОПРОВЕРГНУТА ПРОГОНОМ

> Подтверждено владельцем в игре: **в открытом поле отлетает нормально в сторону,

### 11.1. Ванильный pathfinder НИКОГДА не возвращает «нет пути» (проверено по исходнику 1.20.1)

`PathFinder.findPath(...)`, финальный блок:

```java
    : $$6.stream()                                   // ← цель НЕ достигнута
        .map($$1x -> this.reconstructPath($$1x.getBestNode(), $$2.get($$1x), false))
        .min(Comparator.comparingDouble(Path::getDistToTarget)…);
return !$$18.isPresent() ? null : $$18.get();
```

Даже когда цель недостижима, ваниль строит путь **до ближайшего достигнутого узла**
(`getBestNode()`), с `reached = false`. То есть навигация всегда даёт мобу
**направление на выход**, а `PathNavigation.tick()` ведёт его туда.

### 11.2. Мы этот путь выбраковываем своим выдуманным порогом

[`isUsablePath()`](../../../src/main/java/com/phian404/survivalpoints/entity/BaseGuardianEntity.java:1625):

```java
return path != null && path.getNodeCount() >= GuardianTuning.DETOUR_MIN_NODES; // = 2
```

Ванильный путь к ближайшему достижимому узлу в углу часто состоит из **1 узла**
(стартовый узел = best node). Мы объявляем его «непригодным» и:
1. отбрасываем — лишая стража единственного направления на выход;
2. перебираем 6 лучей по `DETOUR_LOOKAHEAD = 2.0` — в углу между двумя стенами
   все шесть дают тоже 1 узел;
3. в финальной ветке (`:1772-1777`) всё равно делаем `moveTo(direct)` — с тем самым
   1-узловым путём, который `PathNavigation.moveTo()` считает **уже пройденным**.

### 11.3. Полная цепочка в мечевом бою

```
MeleeAttackGoal.tick()               → moveTo(target)      путь есть, страж идёт
наш markMoveIntent()                 → stuck копится (hColl / нет смещения)
detourStuckTicks >= 5
  → followPathDetouring()
      прямой путь 1 узел             → isUsablePath = false   ← ВЫБРОШЕН
      веер 6 лучей                   → все 1 узел             ← ВЫБРОШЕНЫ
      финальная ветка                → moveTo(1 узел)         ← «уже пройден»
  → навигация done, шаг не заказан
MoveControl.tick(), operation = WAIT → setZza(0)
```

**Итог: страж не двигается не потому, что не может, а потому что никто не просит
шаг.** Это подтверждается снимками §3.3 дословно: `заказ=WAIT`, `strafe=false`,
`zza=0.000`, `gPos` не меняется, при этом `hColl` мигает — то есть стена рядом,
но выхода не ищут.

Дополнительно замыкает петлю ванильный `MeleeAttackGoal`: он пересчитывает путь
только при `distanceToSqr(pathedTarget) >= 1.0` или 5 %/тик. Игрок стоит →
пересчёта нет → шаг 11.3 повторяется вечно.

### 11.4. Почему удар «включает» зависание

Удар даёт `knockback` (§7.6): `vy = min(0.4, vy/2 + strength)` = 0.361, подъём
0.96 блокa. Горизонтальная часть отброса гасится стеной, вертикаль остаётся →
подскок **строго на месте**, потому что после приземления шаг снова не заказан
(§11.3). В поле горизонтальная часть проходит → отлёт читается нормально.

**То есть подъём на месте — следствие, а не причина.** Причина одна: **стража
лишили навигационного пути и не дали нового.**

### 11.5. Корневая правка (одна, без костылей)

**Не подменять ванильную навигацию своим путём.**

- Убрать вызовы `followPathDetouring()` из [`GuardianMeleeAttackGoal.tick()`](../../../src/main/java/com/phian404/survivalpoints/entity/ai/GuardianMeleeAttackGoal.java:149)
  и вместе с ним — триггер `markMoveIntent()`/`detourStuckTicks`, который его включает.
- Удалить `followPathDetouring()`, `isUsablePath()`, `DETOUR_ANGLES_DEG`,
  `DETOUR_LOOKAHEAD`, `DETOUR_MIN_NODES`, `DETOUR_RETRY_TICKS`, `DETOUR_TRIGGER_TICKS`,
  `detourAngle*`, `detourStuckTicks`, `detourReported`, `markMoveIntent`, `markStandIntent`.

Движение в мечевом бою остаётся ванильным: `MeleeAttackGoal` → `PathNavigation` →
`MoveControl`. Тогда при упоре ваниль сама отдаёт путь к ближайшему достижимому
узлу, и страж **выходит из стены вбок**. Ничего не изобретаем.

**Что это НЕ трогает:** отход в панике/дальнем бою (`strafeWithSpeed`, `keepYaw`) —
он живёт в других голах, и его судьба решается отдельно (§10.4), чтобы не менять
вид отступления в этом же шаге.

**Проверка:** прижать стража к стене с мечом → он должен **сместиться вдоль
стены** (в логе `gPos` меняется при `hColl=true`), а не стоять с `заказ=WAIT`.
После удара — отлетать вбок, а не подпрыгивать на месте.

**Риск:** если после удаления страж снова начнёт «стоять у стены», значит
виноват уже не наш обход, а `MELEE_IDLE_REPORT_TICKS`-ветка или радиус удара —
и это будет видно по смене `gPos` в логе.

### 9.6. Один прогон, который закрывает все оставшиеся вопросы

Сценарий: загнать стражa к стене, **бить его, пока он прижат** (это ваш случай),
и держать `/sp_snap` каждые 5 тиков. Нужны три новых поля — без них вопросы
«внутри блока ли он» и «куда смотрит голова» останутся гипотезами:

| Поле | Зачем |
|---|---|
| `blockPos` + `блокВНогах=<state> + коллизия=да/нет` | прямо проверит второй источник прыжка (§7.6): `!shape.isEmpty()` |
| `onGround` **из `customServerAiStep`** (после физики) | сейчас `onGround` пишется в `tick()`, уже после `aiStep`, и не видит момент отрыва |
| `yHeadRot` + `ошибкаГоловы = wrapDegrees(yHeadRot − wantYaw)` | единственный способ проверить «не смотрит на меня»; сейчас в логе головы нет вообще |

Плюс `qColl` (вертикальное столкновение сверху) — оно отличит «уткнулся макушкой» от «стоит на земле».
