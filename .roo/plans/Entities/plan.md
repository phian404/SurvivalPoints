# План: базовый NPC, роли и назначение стража

## Архитектурное решение

Использовать отдельные entity type для базового NPC и стража, объединённые общей базовой сущностью с сохраняемой идентичностью и данными выжившего. Не превращать `BaseGuardianEntity` в универсальную сущность с условными ветками ролей: его текущие боевые AI, синхронизация оружия, атрибуты и диагностика остаются специфичными для стража.

Смена роли создаёт сущность нужного типа и заменяет старую. Runtime Minecraft Entity UUID при этом получает новое значение. Сохранять старый runtime UUID не требуется: в Forge/Minecraft 1.20.1 `Mob.convertTo(...)` создаёт новую сущность, а менеджер сущностей регистрирует UUID с проверкой уникальности; ручное переиспользование UUID потребовало бы рискованного вмешательства в регистрацию. Вместо этого лагерные связи используют постоянный NPC identity UUID, который переживает замену типа.

## Этапы реализации

> Этап 3 (женский торс и нагрудная броня) реализован и описан в
> [`AI_CONTEXT.md`](../../../src/main/java/com/phian404/survivalpoints/AI_CONTEXT.md) (раздел «Геометрия торса и броня»).
> Ниже — этапы 0–8 исходной архитектуры NPC.

1. **Общая идентичность и состояние NPC**
   - Определить общую базовую сущность для базового NPC и `BaseGuardianEntity`.
   - Добавить отдельный постоянный identity UUID, роль, индекс скина и необязательные camp/post UUID.
   - Синхронизировать клиенту только визуально/интерактивно необходимые данные; сохранять состояние в NBT.
   - Критерий готовности: identity/роль/скин восстанавливаются после сохранения и загрузки, а отсутствие необязательной лагерной привязки поддерживается штатно.

2. **Обратная совместимость лагерных назначений**
   - `CampRecord` и `CampPost` должны ссылаться на постоянный NPC identity UUID.
   - Для старых стражей без identity-поля использовать их существующий Entity UUID как legacy identity, чтобы не потерять текущие записи `guardianPosts`.
   - При чтении старого NBT поста сохранить legacy UUID без принудительного пересоздания назначения; при последующей миграции сущности сохранить именно его.
   - Критерий готовности: старое сохранение лагеря загружается с прежним числом назначений, а новые назначения используют identity UUID.

3. **Базовый NPC и spawn egg**
   - Зарегистрировать отдельные entity type, атрибуты, renderer и отдельное яйцо призыва; добавить яйцо в творческую вкладку и локализации.
   - Базовый NPC по умолчанию нейтрален/пассивен и не запускает guardian-goals.
   - Критерий готовности: яйцо создаёт базового NPC, который не атакует цели и корректно сохраняется.

4. **Случайный скин**
   - Выбирать скин только на сервере при первичном создании, из закрытого набора существующих ресурсов.
   - Синхронизировать индекс скина через entity data; сохранять его в NBT, не выбирать заново при загрузке.
   - Общий renderer выбирает текстуру по индексу и обслуживает обе entity type.
   - Критерий готовности: клиенты видят одинаковый вариант; каждый вариант допустим; после перезахода скин остаётся тем же.
   - Готовые скины для будущего набора — в [`assets-source/ReadyToUseSkins/`](../../../assets-source/ReadyToUseSkins/) (14 обычных NPC + 4 лидера, 64×64; визуально не проверены). Лор лидеров — [`SurvivalPoints_Leaders.md`](../../../assets-source/ReadyToUseSkins/SurvivalPoints_Leaders.md).

5. **Единый сервис создания и назначения ролей**
   - Создать серверный `RoleAssignmentService`/фабрику, принимающий исходного NPC, целевую роль и необязательный контекст лагеря.
   - Сделать этот сервис единственной точкой перехода: ручное взаимодействие, будущий UI управления лагерем и генерация/размещение NPC в лагере вызывают один механизм.
   - Сервис должен поддерживать создание сущности сразу нужного типа, поэтому лагерной генерации не требуется сначала спавнить базового NPC.
   - Критерий готовности: все три вызывающих сценария используют общую проверку, подготовку и commit операции; независимому NPC не нужен camp ID.

6. **Безопасная замена базового NPC на стража**
   - Для прототипа назначать роль взаимодействием с базовым NPC при использовании арбалета; выполнение и проверка предмета — на сервере, клиент получает корректный результат взаимодействия.
   - До удаления исходника создать новую сущность, перенести identity UUID, скин, необязательные camp/post UUID, custom name, позицию/поворот, здоровье, флаги persistence/invulnerability, экипировку и другие согласованные общие данные.
   - Если создание или добавление новой сущности не удалось, не удалять исходную. Исходник удалять только после успешного добавления и обновления лагерной привязки.
   - Runtime UUID новой сущности оставить новым; не вызывать ручной `setUUID` для повторного использования UUID и не модифицировать внутренний реестр Minecraft.
   - Для лагерного NPC обновить связь CampRecord/CampPost через identity UUID без освобождения поста; независимого NPC преобразовывать без лагерных записей.
   - Критерий готовности: после перехода страж имеет новый runtime UUID, прежний identity UUID и скин, занимает тот же пост; отсутствуют дубли сущностей и «призрачные» назначения.

7. **Подключение поведения стража**
   - Оставить существующие `Guardian*Goal`, `GuardianMoveControl`, `GuardianTuning`, систему состояний, атрибуты и диагностику в `BaseGuardianEntity`.
   - Перенести только общие данные/рендер в базовую сущность; не переписывать боевую логику без необходимости.
   - Критерий готовности: назначенный страж использует прежние ranged/melee/panic AI и экипировку; обычный NPC не запускает эти системы.

8. **Проверки и приёмка**
   - Проверить ручное назначение через арбалет, создание сразу стражем через API генерации, независимого NPC без лагеря и будущую точку вызова UI.
   - Проверить NBT до и после трансформации, загрузку старого лагерного NBT, identity и связь поста, runtime UUID uniqueness, синхронизацию скина и поведение на dedicated server/client.
   - Запустить `gradlew.bat compileJava`; провести игровую проверку всех вариантов.
   - Критерий готовности: сборка успешна, старые записи не теряются, один NPC существует до/после перехода, роль и скин совпадают на сервере и клиентах.

## Проверенные API / ограничения

Для Minecraft Forge 1.20.1 MCP подтверждены `Mob.mobInteract(Player, InteractionHand)`, `Mob.finalizeSpawn(...)`, `Mob.convertTo(EntityType, boolean)`, `EntityType.Builder.of/sized/clientTrackingRange/build`, `EntityDataSerializers.BYTE/INT`, а также методы идентичности Entity. `Mob.convertTo(...)` не переносит кастомные поля NPC и не сохраняет автоматически runtime UUID; `ServerLevel` регистрирует сущность через менеджер с проверкой уже загруженных UUID. Поэтому перенос identity/NBT и обновление лагерных ссылок должны быть явной частью операции, а runtime UUID рекомендуется оставить новым.
