# CAMP_IDEAS.md — Идеи и предложения по системе лагерей SurvivalPoints

> **Статус:** черновик идей, не утверждённое техническое задание.
>
> Документ предназначен для сохранения предложений на будущее. Он не является разрешением
> немедленно реализовывать перечисленные механики. Перед реализацией владелец должен согласовать
> конкретные решения и перенести утверждённые пункты в `DESIGN_CAMP_SYSTEM.md`,
> `DESIGN_CAMP_SOCIAL.md` и/или `ROADMAP.md`.
>
> **Текущий приоритет проекта:** продолжать текущую работу над тетивой и стражем.
> Не переключаться на реализацию системы лагерей только из-за наличия этого документа.

---

## 1. Основные фракции и лагеря

**Предложение:** предусмотреть четыре основные фракции, у каждой — один крупный основной лагерь. Позже можно добавить небольшие аванпосты, принадлежащие этим фракциям.

- Не создавать отдельную реализацию лагеря для каждой фракции.
- Использовать общую систему лагерей и отдельные профили фракций.
- Профиль фракции потенциально может задавать идентификатор, специализацию, внешний вид, характерные ресурсы и исходные отношения с другими фракциями.
- Названия, тематики и окончательные различия четырёх фракций пока не утверждены.

**Почему:** общая реализация должна уменьшить дублирование кода и упростить балансировку.

**Статус:** идея для обсуждения.

## 2. Размещение основных лагерей в мире

**Предложение:** использовать гибридный подход к генерации основных лагерей.

- Для каждого основного лагеря хранить состояние размещения и его координаты после успешного выбора места.
- Перед строительством проверять пригодность участка: рельеф, уклон, воду, пересечения с другими структурами и расстояние до уже размещённых лагерей.
- Если участок не подходит, пробовать другой.
- Если подходящее место не найдено за одну попытку, не терять лагерь навсегда: предусмотреть возможность повторного поиска.
- Разделять регистрацию лагеря в данных и фактическое размещение его блоков в мире.
- Использовать подготовленные планировки с ограниченными вариациями, а не пытаться сразу строить полностью процедурные огромные базы.

**Почему:** это снижает риск появления лагерей в непригодных местах и позволяет контролировать размер реализации.

**Статус:** идея для обсуждения; алгоритм и технические детали нужно спроектировать отдельно.

## 3. Малые аванпосты

**Предложение:** не генерировать множество полноценных лагерей с самого начала.

Возможная последовательность:
1. Сначала обеспечить работу одного базового лагеря.
2. Затем реализовать четыре основных лагеря.
3. После проверки производительности и генерации добавить небольшие аванпосты.

Аванпосты могут иметь меньше NPC, меньше блоков и ограниченный набор функций.

**Статус:** предварительная рекомендация.

## 4. Стартовая книга и журнал мира

**Предложение:** разделить вводную информацию и постоянно обновляемые данные.

- Стартовая книга знакомит игрока с миром, правилами выживания и существованием фракций.
- Не раскрывать в ней автоматически все координаты лагерей, если игрок ещё не обнаружил их.
- Отдельный журнал мира открывается назначенной клавишей.
- Журнал потенциально показывает известные лагеря, текущую репутацию, доступные задания и историю важных событий.
- Источником актуальных игровых данных должна оставаться серверная система сохранения; книга и интерфейс лишь отображают соответствующие сведения.

**Почему:** это не дублирует игровое состояние и сохраняет смысл исследования мира.

**Статус:** идея для обсуждения. Нужно согласовать, какие сведения известны игроку с начала игры.

## 5. Отношения между фракциями

**Предложение:** использовать существующую систему репутации и отношений, а не создавать отдельные несвязанные шкалы для каждой механики.

Возможный вариант начального баланса:
- Большинство фракций изначально нейтральны или настороженны.
- Одна фракция может быть изначально враждебной, если это поддерживает выбранный лор.
- Враждебность должна иметь понятные границы и правила поведения, чтобы игрок не подвергался неожиданным атакам в любой точке мира.

Необходимо отдельно определить, чем отличаются личная репутация игрока у фракции и отношения между двумя фракциями.

**Статус:** открытый вопрос; количество и характер враждебных фракций не утверждены.

## 6. Рейды на личный лагерь

**Предложение:** добавить рейды только после того, как стабильно работают охрана, посты, тревога и ворота.

Потенциальные ограничения:
- перерыв между рейдами;
- конечный размер атакующей группы;
- предупреждение или понятный сигнал о начале угрозы;
- возможность подготовиться или улучшить отношения;
- защита от полного и необратимого уничтожения личного лагеря одним событием.

Если рейды будут реализованы, их состояние должно сохраняться, чтобы перезагрузка мира не запускала событие повторно и не сбрасывала его некорректно.

**Статус:** идея на поздний этап, не задача для текущей разработки.

## 7. Межлагерная торговля

**Предложение для первой версии:** доставка через радио с таймером, без физически перемещающихся караванов.

Возможный поток:
1. Игрок выбирает доступную фракцию и товар.
2. Сервер проверяет условия, стоимость и наличие ресурсов.
3. Заказ создаётся и получает устойчивый идентификатор.
4. Заказ хранится в состоянии ожидания доставки.
5. По завершении времени заказ становится доступен для получения.
6. Получение завершает заказ ровно один раз.

Нужно заранее определить поведение при выходе игрока из мира, перезагрузке, потере связи с радио-вышкой и нехватке товара.

Физические караваны, охрана и засады могут быть отдельным расширением после проверки базовой торговли.

**Статус:** предварительная рекомендация; правила оплаты и условия доставки требуют согласования.

## 8. Принципы управления объёмом работ

- Не реализовывать все системы одновременно.
- Сначала завершать и проверять фундаментальные механики, затем добавлять зависимые функции.
- Не создавать отдельные классы и подсистемы без необходимости, если задачу можно выразить данными и общей логикой.
- Для каждого этапа заранее определять проверяемые критерии готовности.
- Перед началом реализации сверять этот список с `ROADMAP.md`, `DESIGN_CAMP_SYSTEM.md` и `DESIGN_CAMP_SOCIAL.md`.
- Если документы расходятся, не выбирать вариант молча: зафиксировать противоречие и запросить решение владельца.
- Проверять API Minecraft Forge именно для целевой версии 1.20.1; не использовать API более новых версий без проверки совместимости.

5. Как различаются личная репутация игрока и отношения между фракциями?
6. Какие ресурсы и условия нужны для межлагерной торговли?

## 10. Правило использования этого документа

Этот файл — **банк идей**, а не текущий план реализации.

Перед реализацией каждой идеи:
1. Обсудить и утвердить её с владельцем.
2. Проверить зависимости и противоречия с действующими документами.
3. Перенести утверждённое техническое решение в профильный дизайн-документ.
4. Обновить `ROADMAP.md`, если меняются этапы или зависимости.
5. Только после этого планировать код и тестирование.

До отдельного решения владельца текущая работа над тетивой и стражем остаётся приоритетом.
