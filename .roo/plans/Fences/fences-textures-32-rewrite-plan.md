# План: текстуры ограждений 32×32 по образцам заказчика

> **Статус: НЕ РЕАЛИЗОВАНО и НЕ УТВЕРЖДЕНО.** Разрешение текстур ограждений (16 / 32 / 64) — **нерешённый конфликт**, см. §2.
> Действующее состояние кода: `fences-v1.1.7-implementation-plan.md` сообщает о текстурах 16×16. Этот документ описывает предлагаемый переход на 32×32 и **не является** действующим решением.
> Эталоны-образцы: `assets-source/NonGit/reference/5Assets/` (файлы `*32x32.png`).

## 2. Нерешённый конфликт разрешения

| Источник | Утверждение |

| Этот документ | заменить те же 5 текстур на **32×32** |

Оба утверждения относятся к одному набору файлов. Решение не принято. Фактические размеры PNG в `src/main/resources/assets/survivalpoints/textures/block/` инструментально не проверялись в рамках этого аудита.

Пока решение не принято:
- не менять разрешение существующих PNG;
- не пересчитывать UV моделей `section_*` под другое разрешение;
- не считать ни 16×16, ни 32×32 утверждённым стандартом.

Волна чисто визуальная. Не меняет геометрию, логику, коллизии, lang.

## 1. Задача

Заменить 5 своих текстур ограждений на 32×32 по образцам из [`assets-source/NonGit/reference/5Assets/`](../../../assets-source/NonGit/reference/5Assets) (файлы `*32x32.png`).

Столб не меняется: `post_core` остаётся на ванильных `stripped_oak_log` / `stripped_oak_log_top`.

## 2. Что НЕ меняется

`SectionBlock.java`, `PostBlock.java`, `ModBlocks`, `ModCreativeTabs`, lang, коллизии `SHAPE_Z`/`SHAPE_X`, `post_core.json`, `post.json`, blockstates.

Разрешение PNG не привязано к размеру блока: UV `0..16` покрывает всю текстуру при любом разрешении.

## 4. Арифметика UV — определяет, что вообще видно

В моделях UV заданы в пространстве `0..16`. При текстуре 32×32 окно `v a..b` выбирает строки `2a..2b`.

| Файл | Грань | UV-окно в модели | Строки текстуры при 32×32 | Итог |
|---|---|---|---|---|
| `plank` | `north`/`south` | `u 0..2`, `v 0..5` | `0..10` | видна только верхняя четверть |
| `plank` | `east`/`west` | `u 1..17`, `v 0..5` | `0..10` | то же |
| `wire` | `north`/`south` | `u 0..2`, `v 6..10` | **`12..19`** | **нить образца сюда не попадает** |
| `wire` | `east`/`west` | `u 0..16`, `v 6..10` | `12..19` | то же |
| `mesh` | `east`/`west` | `u 0..16`, `v 0..16` | все | полное покрытие |
| `sheet` | панель | `u 0..16`, `v 0..16` | все | полное покрытие |
| `sheet` | рейка | `u 0..16`, `v 0..2` | `0..4` | верхние 4 строки |
| `metal` | рейка | `u 0..16`, `v 0..2` | `0..4` | верхние 4 строки |

## 5. Блокирующая находка: `wire`

[`wire32x32.png`](../../../assets-source/NonGit/reference/5Assets/wire32x32.png:1) содержит **две** нити (≈ строки 10 и 22). Модель сэмплит только строки `12..19`, то есть пустоту между ними → **проволока отрисуется невидимой**.

Причины: у нас два отдельных 2-px элемента (`Y 4..6` и `Y 12..14`), каждый со своим окном `v 6..10`. Образец нарисован под другой UV-раскладкой.

Варианты:

- **A (рекомендуется, 0 правок JSON).** Рисуем `wire.png` в 32×32 так, чтобы значимая зона попала в строки `12..19`: одна нить по центру окна (строки `15..17`, тень на `18`), X-шипы с периодом 16 текселей, остальное прозрачно. Стиль и палитра — из образца. Отклонение от образца: одна нить вместо двух (как и было в 16×16, где одна нить лежала ровно в окне).
- **B (правка модели).** Сдвинуть UV на `v 4..8` или `v 8..12` под положение нитей образца. Даёт «точь в точь», но требует правки `section_wire.json` и `section_wire_tongue.json` и синхронизации с `plank`.

## 6. Вторая находка: `plank`

Окно `v 0..5` → строки `0..10` из 32. В образце 4 доски на всю высоту; в окно попадёт всего ~1.3 доски.

- **A (рекомендуется).** Уложить рисунок досок в строки `0..10`: 2 доски по 5 строк с тёмным швом между ними. Совпадает с геометрией (`Y 2..7` и `10..15` = доска 5 мировых px), торцы читаются как срез двух досок.
- **B.** Оставить образец как есть → на длинных гранях видна одна доска, ряд досок в мире не читается. Не рекомендую.

## 7. Пофайловая спецификация

Палитра — из образцов (извлекается программно), не из спеки v5.

### 7.1 `sheet.png` — 32×32, непрозрачная
Гофра периодом 8 текселей (4 ребра), ржавые подтёки по образцу, степень износа как у `mesh`. Бесшовность по X обязательна, по Y нет (рейка маскирует).

### 7.2 `plank.png` — 32×32, непрозрачная
Доски уложены в строки `0..10` (§6-A). Волокно вдоль X, прожилки 4–12 текселей, **без крапа** (текущий файл — шумная modulo-заливка, главное расхождение). Тёмная `end-grain` кромка — колонки `x 0..1` и `30..31`. Швы не на границах окна. Бесшовность по X обязательна.

### 7.3 `wire.png` — 32×32, альфа 0/255
Одна нить в строках `15..17` + тень `18` (§5-A). Шипы в `12..19`, период 16 текселей, симметрично по X. Остальное прозрачно.

### 7.4 `mesh.png` — 32×32, альфа 0/255
Ромб периодом 16 текселей (2 ромба на блок, 8 мировых px). Линия 2–3 текселя с одной светлой гранью, ржавые вкрапления. **Бесшовность по обеим осям критична** (стек ярусов, D-17). Торцевой кромки нет.

### 7.5 `metal.png` — 32×32, непрозрачная
Видна только рейка (строки `0..4`), крупные детали там не читаются. Ровный тон + редкие царапины. Максимум `#6E6E72`. Бесшовность не требуется.

## 8. Ограничения (из спеки, сохраняются)

- `wire`, `mesh`: альфа строго `0`/`255`, без полупрозрачных пикселей (cutout → дыры, мерцание).
- Металл не светлее `#6E6E72`.
- Ржавчина единая для `mesh` и `sheet`.
- `end-grain` только у `plank`.

## 9. Инструмент

Скрипт `tools/gen-fence-textures.ps1` **отсутствует** — `tools/` сейчас содержит только `package.json` и `package-lock.json` (зависимость MCP-сервера). Если переход на 32×32 будет утверждён, генератор нужно создать заново. Существующие помощники лежат в `assets-source/AiModelling/scripts/` (`.ps1` и `.js`).

Требуемое поведение будущего генератора: читает `assets-source/NonGit/reference/5Assets/*32x32.png` как эталон палитры, пишет 32×32 по §7 в `src/main/resources/assets/survivalpoints/textures/block/`, печатает отчёт (имя, размер, уникальные цвета, распределение альфы).

Грабли:
- Сохранение только `Bitmap.Save(..., Png)`. `Set-Content -Encoding UTF8` в PS 5.1 даёт BOM → `illegal character: '\ufeff'`.
- Только `Format32bppArgb`.
- Идемпотентность: повторный запуск — те же байты.
